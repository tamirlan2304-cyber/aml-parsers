# Stolen assets parsers

Пайплайн собирает криптоадреса из публичных источников и создаёт Parquet
исключительно в памяти. Telegram и SlowMist объединяются по адресу в объект:

```text
stolen_assets/stolen_assets.parquet
```

DeFiHackLabs имеет другую схему и сохраняется **отдельно**:

```text
stolen_assets/defihacklabs.parquet
```

Отфильтрованный Telegram с прямыми ссылками на сообщения также сохраняется отдельно:

```text
stolen_assets/telegram_investigations.parquet
```

SlowMist с заголовком `Hacked target` сохраняется в собственный объект:

```text
stolen_assets/slowmist_hacked.parquet
```

SoKSPBlockchainInterop с пятью собственными колонками сохраняется отдельно:

```text
stolen_assets/sok_interop.parquet
```

SolidityScan Hack Analysis с четырьмя собственными колонками сохраняется отдельно:

```text
stolen_assets/solidityscan_hack_analysis.parquet
```

Старый `stolen_assets/stolen_assets.parquet` остаётся совместимым трёхколоночным
объединением. Это **не** очищенный Telegram-набор: в нём остаются исторические
строки и данные SlowMist, для которых роли не фильтруются. Для новой задачи
используйте отдельный объект `telegram_investigations.parquet`.

Подключены пять источников:

- `https://t.me/s/investigations` — полная история Telegram через пагинацию
  `?before=<message_id>`;
- `https://hacked.slowmist.io/?c=&page=1` — полный HTML-каталог SlowMist Hacked
  через пагинацию `Page N of M`;
- [SunWeb3Sec/DeFiHackLabs](https://github.com/SunWeb3Sec/DeFiHackLabs) — явно
  подписанные роли адресов в описаниях реальных инцидентов;
- [RafaelAPB/SoKSPBlockchainInterop](https://github.com/RafaelAPB/SoKSPBlockchainInterop)
  — все валидные криптоадреса, опубликованные в таблицах взломов мостов;
- [SolidityScan Hack Analysis](https://blog.solidityscan.com/category/hack-analysis/)
  — явно подписанные адреса атакующих, exploit-контрактов и кошельков с
  похищенными средствами из всех опубликованных статей категории.

ID отдельных файлов внутри медиагрупп Telegram дополнительно извлекаются из
ссылок `?single`, поэтому они не теряются из подсчёта доступных сообщений.
SlowMist отдаёт серверный HTML, поэтому для него не требуются Chrome или
Playwright. Парсер сверяет номер страницы, общее количество страниц и событий,
делает повторные попытки и не принимает незаметно изменившуюся пагинацию.

## Файлы

- `telegram_investigations_parser.py` — парсер конкретного источника;
- `slowmist_hacked_parser.py` — парсер HTML-каталога SlowMist Hacked;
- `defihacklabs_parser.py` — парсер датированных PoC-файлов DeFiHackLabs;
- `sok_interop_parser.py` — парсер таблиц мостов и CSV дат SoKSPBlockchainInterop;
- `solidityscan_hack_parser.py` — парсер статей SolidityScan Hack Analysis;
- `run_and_upload.py` — запуск всех парсеров, объединение и обновление S3;
- `debug_table.py` — печать результата в консоль без S3 и локальных файлов;
- `.env` — настройки источника и фиксированный S3-ключ;
- `.env.example` — шаблон для отдельного окружения;
- `tests/` — проверки HTML, адресов, дат и S3-merge.

`SOURCE_BUILDERS` содержит Telegram и SlowMist. При сборке старого объединения
оба источника явно проецируются на `LEGACY_SCHEMA`, но в собственных таблицах
сохраняют свои дополнительные колонки. `build_output_tables()` возвращает таблицы:
`stolen_assets`, `telegram_investigations`, `slowmist_hacked`, `defihacklabs`,
`sok_interop`, `solidityscan_hack_analysis`.
`build_current_table("all")` сохраняет старый API
и возвращает только объединение Telegram/SlowMist; для всех выходов используйте
`build_output_tables("all")`. CLI обоих файлов использует новый API.

## Схема старого объединения

```text
wallet_address  string, not null
network         string, not null
listed_date     date32, not null
```

Все EVM-адреса записываются с сетью `Ethereum`. Для Telegram используется
UTC-дата сообщения, для SlowMist — дата события из `span.time`. Если адрес
встречается повторно внутри одного или нескольких источников, сохраняется самая
ранняя дата его появления.

## SlowMist: заголовок события

Собственная таблица SlowMist (`slowmist_hacked_parser.OUTPUT_SCHEMA`):

```text
wallet_address  string, not null
network         string, not null
listed_date     date32, not null
hacked_target   string, nullable
```

`hacked_target` — название из HTML-заголовка `<h3>Hacked target: ...</h3>`:
например, `warp.green`, без префикса `Hacked target:`. HTML-разметка и лишние
пробелы убираются; регистр, Unicode и само название сохраняются. Если поле
отсутствует или пустое, записывается `null` (в консоли — пустая ячейка).
Значение берётся только из заголовка события, не из его описания.

Как и раньше, одна строка соответствует одному уникальному адресу. Название
сохраняется **вместе с датой самого раннего события** для этого адреса. При
совпадении дат выбирается непустой заголовок, затем первый по алфавиту без учёта
регистра (при равенстве — сравнение исходных строк). Заголовок более позднего
события не подставляется к ранней дате, даже если у раннего заголовка нет.

`debug_table.py --source slowmist_hacked` выводит все четыре колонки.
`run_and_upload.py --source slowmist_hacked` создаёт Parquet только в памяти
и обновляет **только** `stolen_assets/slowmist_hacked.parquet`. При отсутствии
объекта загружается весь набор; иначе добавляются новые адреса, более ранняя дата
обновляется вместе с заголовком, а название для той же даты может быть дополнено
или исправлено по текущему источнику. Исторические адреса не удаляются. Если
изменений нет, PUT не выполняется. Не запускайте два загрузчика одного объекта
одновременно. Ключ фиксирован отдельно от старого `S3_KEY`, менять `.env` не нужно.
Старый смешанный объект остаётся трёхколоночным и не получает `hacked_target`:
достоверно восстановить названия для его исторических строк невозможно.

SlowMist не предоставляет отдельное структурированное поле «адрес злоумышленника».
Поэтому код извлекает все явно опубликованные и валидные криптоадреса из текста
события и ссылок: это могут быть адрес злоумышленника, получателя, атакованного
контракта или другой адрес, связанный с инцидентом. Роль адреса без отдельной
колонки надёжно определить невозможно.

## Telegram: фильтрация и ссылка на сообщение

Новая схема Telegram (`OUTPUT_SCHEMA`):

```text
wallet_address  string, not null
network         string, not null
listed_date     date32, not null
message_url     string, not null
```

`message_url` имеет вид `https://t.me/investigations/353`. Сохраняется ссылка
на самое раннее подходящее сообщение вместе с его UTC-датой. Для повторов в
один день сравнивается время, затем ID. Для медиагруппы ссылка ведёт на сообщение
с общей подписью, а не на произвольно выбранную соседнюю фотографию.

Правило: не включать адреса жертв, протоколов, пулов ликвидности, токенов, мостов,
CEX, роутеров, служебных контрактов Foundry и тестовые адреса. Реализация:

- проверяется формат/контрольная сумма адреса, затем определяется сеть;
- учитываются подписи **до и после** адреса: `Victim: ...`, `... (victim)`,
  `... — victim`, в том числе явно подписанный постфикс на следующей строке;
- заголовки `Victim`, `KuCoin deposit addresses`, `EVM hot wallets` действуют
  на последующий список; новый заголовок `Theft addresses` переключает контекст;
- само упоминание жертвы/биржи где-то в сообщении не исключает все его адреса;
- распознаются английские и русские подписи, названия распространённых CEX,
  депозитные endpoints, URL токенов/пулов и известные константы Foundry/токенов;
- `<br>` и абзацы сохраняются. Адрес из скрытой ссылки анализируется рядом с
  текстом этой ссылки. Навигационные ссылки вне текста сообщения не собираются;
- произвольные параметры URL, ссылки на гранты и транзакции не считаются
  самостоятельным доказательством адреса;
- исключение по адресу имеет приоритет во **всей загруженной истории**: если
  адрес помечен жертвой/инфраструктурой в одном сообщении, повтор без подписи
  в другом сообщении не возвращает его в таблицу. Это консервативное правило.

Это проверка текстовых подписей, а не универсальная ончейн-классификация.
Если автор не подписал роль адреса или использовал незнакомую формулировку,
фильтр не способен гарантированно определить его принадлежность. Отсутствие
исключающей подписи само по себе не доказывает, что адрес принадлежит атакующему.
Для аудита используйте `message_url` и подробный журнал `--verbose`.

Обновление **отдельного Telegram-объекта** синхронизирует всю текущую отфильтрованную
историю, а не добавляет её к прежним строкам: новые адреса добавляются, изменённые
ссылки/даты обновляются, отсутствующие после перепроверки адреса удаляются из
нового снимка. Иначе старые адреса жертв могли бы остаться навсегда. При неизменном
результате PUT не выполняется. При ошибке/неполной пагинации или пустом результате
загрузка не начинается. HTML страницы ошибки без истории канала не принимается
за конец истории. Одновременные загрузчики одного объекта не поддерживаются.

Старый смешанный объект не мигрируется автоматически: в его трёх колонках нет
данных, позволяющих надёжно восстановить источник и роль каждой старой строки.
Запуск `--source telegram_investigations` обращается только к новому S3-ключу.
Для SlowMist и DeFiHackLabs сохраняется добавление к историческим данным,
а не полная замена снимка.

## Схема и правила DeFiHackLabs

Ровно шесть колонок, все обязательные:

| Колонка | Тип Parquet/Arrow | Значение |
| --- | --- | --- |
| `address` | string | EVM-адрес, нормализованный в нижний регистр |
| `network` | string | `Ethereum` для всех EVM-сетей, включая BSC, Base и Arbitrum |
| `incident_name` | string | Название инцидента из датированного заголовка README |
| `role` | string | Одна из шести разрешённых ролей ниже |
| `incident_date` | date32 | Дата инцидента из README, не дата скачивания/коммита |
| `source_url` | string | Полная ссылка на `.sol` в конкретном Git-коммите, с `#L...` |

Роли присваиваются только при явной подписи в описании:

- `attacker` — `Attacker`, `Attacker EOA`, `Exploiter` и аналогичные точные поля;
- `exploit_contract` — `Attack Contract`, `Attacker Contract`, `Exploit Contract`;
- `exploit_caller` — явно указанный отправитель **исходной** атакующей транзакции;
- `profit_receiver` — явно подписанный получатель прибыли;
- `consolidation` — явно указанная консолидация похищенных средств;
- `laundering` — явно подписанный адрес отмывания, а не просто источник финансирования.

`Attacker` не превращается автоматически в `exploit_caller`. `Funds Receiver`,
`tx.origin`, получение перевода или финансирование через Tornado Cash сами по себе
недостаточны для присвоения роли получателя прибыли/отмывания. Некоторые из шести
ролей могут отсутствовать в результате — код не создаёт неподтверждённые строки.

Принцип отбора — точность важнее количества:

1. Один раз разрешается `main` в Git SHA, затем публичный ZIP этого коммита
   скачивается и читается в памяти. Учётная запись GitHub/API-ключ не нужны.
2. Берутся только файлы `src/test/YYYY-MM/*.sol`, связанные с датированными
   заголовками корневого README и `past/YYYY/README.md`. При противоречивой
   дате/названии файл пропускается с предупреждением.
3. Извлекаются явные поля ролей в комментариях уровня файла, до первого контракта
   (в том числе после объявлений интерфейсов). Строки кода, `vm.prank`, `deal`,
   `makeAddr`, константы `attacker` и тела тестов не являются положительным доказательством.
4. Отсекаются хеши транзакций, повреждённые адреса, короткие/типовые заглушки,
   нулевые адреса и известные служебные адреса Foundry. Адреса с признаками жертвы,
   токена, пула, моста, CEX, роутера или служебной инфраструктуры исключаются.
   Типизированные токены и явно названная инфраструктура в коде используются
   только для исключения, но не для назначения роли.
5. При конфликте допустимой и исключаемой роли внутри инцидента побеждает
   исключение. Неоднозначные подписи, whitehat-репродукции и явно pre-production
   инциденты пропускаются. Пропущенные файлы видны при `--verbose` у парсера.

Важно: атрибуция опирается на подписи авторов DeFiHackLabs. Это не независимая
проверка транзакций через RPC и не официальный санкционный список. Парсер не
гарантирует полноту репозитория или безошибочность его авторов; для автоматической
блокировки нужна отдельная проверка доказательств. `source_url` сохраняет точную
версию доказательства для такого аудита. Solidity/Foundry-код не выполняется.

Одинаковый адрес с разными ролями или в разных инцидентах остаётся в нескольких
строках. Ключ дедупликации: `(address, network, incident_name, incident_date, role)`.
Если есть несколько файлов-доказательств одной строки, выбирается один
детерминированно. Поэтому количество строк и уникальных адресов различается.

Обновление S3: если объекта нет — загружается вся таблица; если есть — добавляются
новые ключи и обновляются ссылки на доказательства существующих ключей. Смена SHA
не создаёт дубликаты. Если изменений нет, PUT не выполняется. Исторические строки
не удаляются автоматически при исчезновении из источника; исправления/отзывы
атрибуции требуют отдельной ревизии. Не запускайте одновременно два загрузчика
одного S3-объекта: read/merge/write не является распределённой блокировкой.

Новые настройки `.env`: `DEFIHACKLABS_REF=main` (можно зафиксировать SHA),
`DEFIHACKLABS_MAX_RETRIES=3`, необязательный `DEFIHACKLABS_REPO_DIR` для локального
клона. Локальный режим читает **закоммиченный HEAD**, не изменения в рабочей папке,
и требует установленный Git. Обычному сетевому режиму Git не нужен.
S3-подключение общее; ключ DeFiHackLabs фиксирован отдельно от прежнего `S3_KEY`.

## SoKSPBlockchainInterop: все опубликованные адреса

Схема `sok_interop_parser.OUTPUT_SCHEMA` — ровно пять колонок:

| Колонка | Тип Arrow/Parquet | Содержание |
| --- | --- | --- |
| `address` | string, not null | Полный проверенный криптоадрес; EVM — в нижнем регистре |
| `network` | string, not null | Для всех EVM-сетей `Ethereum` |
| `hacked_bridge` | string, not null | Имя моста из строки исходной таблицы |
| `incident_date` | date32, nullable | Дата из CSV, если запись сопоставлена; иначе `null` |
| `link` | string, not null | GitHub-ссылка на исходную строку с адресом, закреплённая на SHA |

Источники внутри репозитория:

- `bridge_hacks/txs_and_addresses_hashes.md` — полные адреса и подписи;
- `bridge_hacks/incident_response.md` — соответствующие объявления об инцидентах;
- `data/all_bridge_hacks.csv` — даты в формате **день/месяц/год**.

Парсер разрешает `main` в SHA и загружает только эти три текстовых файла одной
версии, целиком в память. Сокращённые таблицы из README не используются. Git,
браузер и GitHub-аккаунт не требуются. Python/R/Jupyter-код репозитория не запускается.
HTTP-ошибки 429/5xx повторяются, размер каждого ответа ограничен 2 MiB.

По запросу пользователя фильтр ролей для **этого источника** убран. Функция
`extract_addresses()` извлекает все полные валидные адреса из текста обеих
Markdown-таблиц, свободных описаний, Markdown/HTML-ссылок и параметров URL
(включая URL-кодирование). Наличие `Attacker`/`Exploiter` больше не требуется;
`Addresses on Ethereum`, неизвестные подписи и вообще отсутствие подписи также
допустимы. Слова victim/token/pool/bridge/CEX/Foundry или uncertain не исключают
синтаксически валидные адреса. Прежнее имя `extract_attacker_addresses()` оставлено
как совместимый вызов новой функции, но строгого отбора больше не делает.

Сохраняется проверка формата адреса и доступной для его типа контрольной суммы;
EVM проверяется как полный 20-байтовый адрес. Хеши транзакций не обрезаются до
адресов, повреждённые значения не принимаются. Внешние страницы/списки
Nomad/Pastebin не скачиваются: включаются только адреса, непосредственно
присутствующие в загруженных таблицах, в том числе в самих URL. Роль адреса код
теперь **не определяет**: строка означает упоминание в контексте инцидента,
а не доказанную принадлежность атакующему. Фильтры других парсеров не меняются.

Даты требуют отдельного сопоставления, поскольку один мост мог быть взломан
несколько раз. Две полные Markdown-таблицы сопоставляются по порядку строк после
проверки совпадения числа строк и всей последовательности названий мостов.
Несоответствие прерывает обработку до обращения к S3. Это опирается на параллельный
порядок исходных таблиц; перестановку двух строк с одинаковым именем нельзя
обнаружить только по их названиям — для аудита сохраняется точная версия источника.

Для выбора CSV-записи используются нормализованное имя моста и год/месяц
публичного объявления. Время объявления извлекается из Snowflake ID уже имеющейся
ссылки, без запросов в X/Twitter ([описание ID](https://docs.x.com/fundamentals/x-ids)).
**Дата объявления не записывается вместо даты взлома**: сохраняется именно дата
выбранной строки CSV. Если даты противоречат друг другу, нет совпадения или
подходит несколько записей, выводится WARNING, а `incident_date` остаётся `null`.
Если объявления нет, дата допустима только при единственной записи моста в CSV
и единственной строке этого моста в таблице. Ошибки дат в самом CSV автоматически
не исправляются. Таким образом, поле содержит дату по исследовательскому источнику,
а не независимо подтверждённое время атакующей транзакции.

Ключ повторов — `(address, network, hacked_bridge, incident_date)`; повторы одного
EVM-адреса на ETH и BSC в одном инциденте схлопываются. Один адрес в разных
инцидентах может дать несколько строк. Ссылка вида
`https://github.com/RafaelAPB/SoKSPBlockchainInterop/blob/<SHA>/bridge_hacks/txs_and_addresses_hashes.md#L17`
ведёт прямо к записи с адресом. Если адрес встречается только во второй таблице,
ссылка ведёт в `incident_response.md`; повтор в обеих таблицах не создаёт дубликат
одного инцидента. Исходный файл CSV с датой находится в том же SHA.

S3: отдельный фиксированный ключ `stolen_assets/sok_interop.parquet`. Если объекта
нет, загружается весь набор; иначе добавляются новые ключи и обновляются ссылки
существующих записей при смене SHA. Неизменный результат повторно не загружается.
Исторические строки не удаляются; исправление даты меняет ключ и требует отдельной
ревизии старой записи, в том числе при уточнении прежнего `null`. Два одновременных
загрузчика одного объекта не поддерживаются. При ошибке или пустом результате
S3 не обновляется. Parquet создаётся в памяти, локальный файл не сохраняется.

Настройки необязательны: `SOK_INTEROP_REF=main` (также можно указать SHA) и
`SOK_INTEROP_MAX_RETRIES=3`. Значения по умолчанию встроены, `.env` менять не нужно;
примеры добавлены в `.env.example`.

Проверка 27.08.2026, SHA `016a22ac113c1ac419060f982000605f14e23d93`:
18 строк инцидентов проверены; после снятия фильтра получено **19 выходных строк,
18 уникальных адресов в 8 инцидентах** (раньше было 13 адресов).
Из уникальных адресов 16 EVM (`Ethereum`) и 2 Bitcoin. Добавились адреса
PolyNetwork, Chainswap, Thorchain #2 и Boy x Highspeed. Адрес
`0x3a196410a0f5facd08fd7880a4b8551cd085c031` встречается в тексте Thorchain #2
и в параметре ссылки Qubit, поэтому сохранены две строки разных инцидентов.
Связь с Qubit здесь отражает содержимое источника, а не независимую атрибуцию.
У PolyNetwork, Chainswap и Thorchain #2 дата осталась `null` из-за
противоречивых/неоднозначных записей CSV; сами адреса из-за этого не теряются.

## SolidityScan Hack Analysis

Схема `solidityscan_hack_parser.OUTPUT_SCHEMA` — ровно четыре обязательные колонки:

| Колонка | Тип Arrow/Parquet | Содержание |
| --- | --- | --- |
| `address` | string, not null | Полный проверенный криптоадрес; EVM — в нижнем регистре |
| `network` | string, not null | Для всех EVM-сетей `Ethereum`, как в остальных парсерах проекта |
| `incident_date` | date32, not null | Первая явно указанная дата инцидента из обзорной части статьи |
| `incident_name` | string, not null | Заголовок статьи без суффикса `Hack Analysis` |

Парсер читает все опубликованные статьи категории через публичный WordPress REST
API `wp-json/wp/v2/posts?categories=39`. Используются заголовки `X-WP-Total` и
`X-WP-TotalPages`: изменение пагинации, неполный ответ, повтор post ID/URL,
невалидный JSON или несоответствие общего количества прерывают запуск до S3.
Каждый ответ ограничен 8 MiB, для 429/5xx действуют повторные попытки.

Из сокращённо отображаемой ссылки берётся полный адрес из `href`. Принимаются
только явные подписи `Attacker Address`, `Attacker EOA`, `Attack Contract`,
`Exploit Contract`, `Malicious Contract`, `Stolen Funds Parked At`, `Receiver`,
`Consolidation` и эквивалентные варианты. Адреса жертв, уязвимых/официальных
контрактов, funder-кошельки, произвольные адреса из повествования и исходного кода
не включаются. Хеш транзакции не обрезается до 20-байтового EVM-адреса.

Дата публикации WordPress не подставляется вместо даты взлома. Поддерживаются
английские варианты `April 26, 2026`, `11th August 2025`, `31st Oct, 2023`.
Если адреса есть, но точный год/месяц/день в обзорной части не указан, статья
пропускается с WARNING. На проверке 31.08.2026 API вернул 194 статьи: принято
160 датированных статей, сформировано 316 строк и 311 уникальных адресов. Ronin
пропущен, потому что источник пишет `On March 29` без года.

Ключ строки — `(address, network, incident_name, incident_date)`: повтор адреса
в одной статье схлопывается, но тот же адрес в другом инциденте сохраняется.
Отдельный фиксированный S3-ключ —
`stolen_assets/solidityscan_hack_analysis.parquet`. При первом запуске загружается
вся таблица, затем добавляются только новые ключи; история не удаляется. Если
изменений нет, PUT не выполняется. Настройка `SOLIDITYSCAN_MAX_RETRIES=3`
необязательна; URL, категория и S3-ключ зафиксированы в коде.
